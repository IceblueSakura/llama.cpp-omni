# 本地算子提交与验收

本目录属于 `llama.cpp-omni-operators` / `fix/upstream-operators`，记录本地批次验收与 Draft PR 的交付门槛。开发按[修复包规划](../upstream-operator-packages.zh.md)推进：同一批的包逐一核对依赖、统一验收和交付，不按上游提交逐项停顿。既有提交及记录保留。优先本机 CPU/CUDA/Vulkan，可延期平台明确记录，不以其他平台结果代验。

## 每个提交的约定

- 每批附一份验收文档，使用 `<日期>-<批次/主题>.md`；已有子项证据可直接引用。提交以依赖和可独立回退的修复包为界，不为补写 SHA 再制造递归提交。记录目标路径的独立结果及最终组合树的结果。
- 必须记录：本地输入基点、原始`llama.cpp`/`ggml`仓库及完整commit ID、抽取范围与必要依赖、本地适配、验证命令/配置/设备、实际执行/拒绝数量、退出状态、红绿或其他决定性证据、未覆盖项及PR拆分建议。
- 无直接上游来源的适配明确标为本地修改，不编造来源。文档或工作流提交同样有独立验收说明，注明无新增上游实现。
- 本地commit可用简洁主题，不强制公开PR的双语正文等格式；保留准确的来源和AI辅助事实于验收文档，公开提交时由人类重新审阅、组织及披露。
- 实际提交身份/来源仍须真实；不改全局Git配置。维护小而可验证的提交，避免仅为凑粒度拆出不能独立工作的中间状态。

查询某份验收文档对应的原始提交：

```bash
git log --diff-filter=A --format='%H %s' -- docs/development/operator-acceptance/<文件>.md
```

## 边界与证据

默认只使用本机可验收的CPU/CUDA/Vulkan子项；HIP、ARM、其他GPU等也按实际设备能力单独判断，不自动视为有条件。实现、构建、数值验收、动态检测、性能和模型端到端状态分别记录。已有构建可在相同工作区和配置下定向增量复用，迁移前旧绝对路径cache不可复用。

`build-*/evidence/` 保留原始日志、探针、manifest 和 job 元数据，全部 ignored；稳定结论写入验收文档，不把二进制、日志或权重提交到 Git。

## PR 功能批准入与拆分规范

2026-11-20 确认按主题拆分 PR，以**可整批验证、出错整批回退、减少过细粒度**为交付原则：

- **Draft PR #156（`pr/ggml-operator-correctness`）** 聚焦 A/B 类纯正确性修复，按功能批（P1–P3）追平后封板评审，不再无限挂载新能力或性能重排。
- **后续主题（Wave 2 能力补齐 P4/P5、Wave 3 可选性能 P6–P9）** 各自开设独立 PR，避免单批争议阻塞已完成的正确性合入，并确保出错时可整支回退。

每批 PR 交付统一满足以下门槛：

1. **依赖齐全。** 从目标 PR 基线选取一个完整功能批的源码和维护测试，核对必要前置、后续修正和实际调用路径。依赖已在基线树中，或随本批一并验证；不可只靠补丁能应用来判断。开发分支的过程文档、根目录 `AGENTS.md` 顺带改动、本地产物、LES 与 CI 修改不进入算子 PR。
2. **整批可回退。** 批内保留少量按依赖排序的逻辑提交，合并开发期过细的碎片提交；在候选树核对整批可逆序回退且不损伤之前已交付的批次。有新批依赖旧批时显式记录顺序。每笔提交保留完整上游 SHA、英文后中文的说明、准确的 AI 披露和与作者身份匹配的 DCO 签署。
3. **在 PR 基线上整批复验。** 记录实际 PR base、导入前 head 和候选树；在目标 PR worktree 现路径下的新建构建目录独立构建并一次性整批验证受影响后端。以非零命中的用例、独立预期、实际调度、退出码和适用的动态检测为证据；开发树通过、仅注册 kernel 或旧路径的构建记录不能代验。后续批改变同一契约时，复验被触及的既有路径。
4. **显式授权发布。** 经用户授权后才在 PR worktree 提交、推送指定 ref、开立新 PR、标记 Ready 或合并；不合并开发分支、不重写已审阅提交。推送后核对 PR head 和 Draft 状态，并在 [主控路线图](../upstream-operator-packages.zh.md) 更新该批状态。

### PR 提交信息中的测试结果

每笔 PR 提交在正文写 `Validation / 验证`，让审阅者不看原始日志也能知道**测了什么、观察到什么、还有什么没验证**。通过率和用例总数只能补充，不能替代以下内容：

- **通过（Passed）**：写出测试目标或算子、关键用例（如 dtype、尺寸、stride、原地或回退）、实际后端及观察结果。用具体的测试名或复验命令定位；动态检测写清工具、路径和结果。区分实际 GPU 执行、预期拒绝和已验证的 CPU 回退。
- **未通过（Failed）**：写出失败用例、实际错误或输出与预期，以及退出状态（如适用）。只有在基线对照后才标为既有问题；尚未归因就照实写。当前候选的范围内失败阻止准入；预期的基线红灯可单列为「基线 → 候选」，不算候选通过或失败。没有观察到失败时，可写「上述已执行检查无失败」。
- **未跑／跳过（Not run / Skipped）**：写明有影响的设备、配置或路径及原因。过滤未命中、后端拒绝、CI 取消和未测试不能计作通过。

注明结果来自单笔提交还是功能组最终候选树。跨提交复验只在组尾汇总，前面的提交仅记其实际单独验证的内容，不把组合结果写成逐笔通过。正文保留关键用例和结论，完整参数、日志和设备细节放验收记录；审阅所需的关键信息不依赖本机 ignored 路径。
